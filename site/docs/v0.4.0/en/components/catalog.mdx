# Catalog

Catalog provides a page-level skeleton for large capability collections that need search and filtering. Use it only when discovering and choosing a capability is the primary task; use a regular list or Resource Grid for small collections.

## Usage

The Catalog root owns page arrangement only. The host implements search, filtering, sorting, installation, and data requests. Compose [Resource Card](/components/resource-card), a list, or a table inside the results region.

```html
<section class="catalog" aria-labelledby="capability-catalog-title">
  <header>
    <div data-catalog-identity>
      <h1 id="capability-catalog-title">Capabilities</h1>
      <p>Find reusable skills, connectors, and work templates.</p>
    </div>
    <div data-catalog-actions>
      <label for="capability-search">Search capabilities</label>
      <input
        class="input"
        id="capability-search"
        type="search"
        placeholder="Search by name or purpose"
      />
    </div>
  </header>
  <div data-catalog-toolbar>
    <div data-catalog-filters aria-label="Capability type"></div>
    <div data-catalog-actions>
      <output data-catalog-count>12 capabilities</output>
    </div>
  </div>
  <div data-catalog-results aria-label="Capability results"></div>
</section>
```

### Parameters

| API | Required | Purpose |
| --- | --- | --- |
| `data-catalog-identity` | Yes | Page title and concise description |
| `data-catalog-actions` | No | Search, sort, view, or ownership actions |
| `data-catalog-featured` | No | A small, justified set of featured items |
| `data-catalog-toolbar` | Recommended | Filters, result count, and sorting |
| `data-catalog-filters` | No | A group of filters with visible selected state |
| `data-catalog-count` | Recommended | Result count after filtering |
| `data-catalog-results` | Yes | Grid, list, table, or state feedback |

## States and variants

`ready` displays stable results. `loading` retains the title, filters, and results dimensions. `empty` explains why the current conditions match nothing and offers a clear-filter path. `error` names the failure and recovery. `partial` indicates pagination or that more results are still loading.

Featured content is not a permanent advertising slot. Keep the set small and explainable. On phones, show complete stacked items instead of clipped horizontal cards that compete with primary results. Different resource types share search and selection rules; visible metadata communicates the type difference.

## React

```tsx
import { useState } from "react";
import { Catalog, useCatalog } from "@a3s-lab/ui/react";

export function CapabilityCatalog() {
  const [query, setQuery] = useState("");
  const control = useCatalog({
    events: {
      input(event) {
        const target = event.target as HTMLInputElement;
        if (target.type === "search") setQuery(target.value);
      },
    },
  });

  return (
    <Catalog ref={control.ref} aria-labelledby="catalog-title">
      <header>
        <div data-catalog-identity>
          <h1 id="catalog-title">Capabilities</h1>
          <p>Find reusable skills, connectors, and work templates.</p>
        </div>
        <div data-catalog-actions>
          <label htmlFor="catalog-search">Search capabilities</label>
          <input
            id="catalog-search"
            className="input"
            type="search"
            defaultValue=""
          />
        </div>
      </header>
      <div data-catalog-toolbar>
        <output data-catalog-count>1 capability</output>
      </div>
      <div data-catalog-results>
        <article className="resource-card"><h2>Code review</h2></article>
      </div>
    </Catalog>
  );
}
```

`useCatalog` observes standard `input` events at the Catalog root and exposes no controller methods. This example makes the hook the only query update path. A conventional React form may omit the hook and use only `onChange` instead.

## Vue

```vue
<script setup lang="ts">
import { ref } from "vue";
import { Catalog, useCatalog } from "@a3s-lab/ui/vue";

const query = ref("");
const control = useCatalog({
  events: {
    input(event) {
      const target = event.target as HTMLInputElement;
      if (target.type === "search") query.value = target.value;
    },
  },
});
const componentRef = control.componentRef;
</script>

<template>
  <Catalog ref="componentRef" aria-labelledby="catalog-title">
    <header>
      <div data-catalog-identity>
        <h1 id="catalog-title">Capabilities</h1>
        <p>Find reusable skills, connectors, and work templates.</p>
      </div>
      <div data-catalog-actions>
        <label for="catalog-search">Search capabilities</label>
        <input
          id="catalog-search"
          :value="query"
          class="input"
          type="search"
        />
      </div>
    </header>
    <div data-catalog-toolbar>
      <output data-catalog-count>1 capability</output>
    </div>
    <div data-catalog-results>
      <article class="resource-card"><h2>Code review</h2></article>
    </div>
  </Catalog>
</template>
```

The Vue composable is the only query update path here. Remove its `input` handler if you choose `v-model` instead. Query, filters, and results remain application state.

## Accessibility

Catalog needs one unique page title. Give the search input a visible or visually hidden label, and express filter selection with `aria-pressed` or equivalent semantics. Announce result count changes through `data-catalog-count` without moving focus or resetting scroll. Loading, empty, and error states retain title and filter context; retrying or clearing filters leaves focus on the triggering control. Featured and result items use real links or buttons—never a clickable card containing nested actions. The host owns queries, pagination, recommendation criteria, installation permissions, and trusted metadata; the component owns information architecture and responsive arrangement.
