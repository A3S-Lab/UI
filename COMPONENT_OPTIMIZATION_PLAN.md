# Component Optimization Plan

## Purpose

This plan turns the current 116-route catalog into a defensible product system. It does not assume that every existing route deserves to remain a standalone component. Each item must first prove a durable user job, a clear ownership boundary, and a complete state model. Visual refinement starts only after those questions are settled.

The plan applies to native HTML, CSS, optional controllers, React and Vue adapters, bilingual documentation, the standalone Playground, and regression evidence. Compatibility is preserved through documented aliases and migration paths; it is not used to protect an incoherent contract indefinitely.

## Authoritative baseline

The baseline was inspected from the current worktree rather than inferred from catalog claims.

- There are 116 English and 116 Chinese component pages: 86 general components and 30 Harness components.
- The machine manifest exposes 116 contracts. Sixty-two declare events or methods; fifty-four are presentation-only.
- The five component ACL files contain 119 scenarios covering all 116 component pages. Ninety-three execute an interaction, twenty-six only establish presence or static state, and fifty-three capture a screenshot.
- Existing snapshot folders contain 31 unique image names, including compositions and state variants. They do not provide systematic visual proof for all 114 components.
- Seventy-seven English guides still contain a generic `Component content` framework example. Presence of React and Vue headings therefore does not prove a truthful integration example.
- The older primitive guides frequently open with markup instead of a user job and omit explicit state, ownership, or accessibility sections. The newer application and Harness guides have stronger product descriptions but still require behavioral and visual proof.
- Contract contradictions already exist. Spinner is described as having no dedicated component while the manifest and adapters publish one. Scroll Area is a scrollbar utility presented as a component. Radio Group lacks a canonical root class. Theme Switcher resolves through several incidental selectors instead of one public root.
- Risk is concentrated in large controllers: File Explorer is 884 lines, Context Menu 679, Combobox 572, Data Grid 516, Device Simulator 501, Select 465, Code Editor 457, and Filter Bar 447. Files over 500 lines must be split by concern before additional behavior is added.

These facts prove catalog coverage, not product quality. A route, manifest row, adapter symbol, or passing presence assertion is only admission evidence.

## First-principles review model

Every component receives a zero-to-three score in each dimension. A component cannot ship when any critical dimension scores below two, even if its aggregate score is high.

| Dimension          | Question                                                                                                                  | Release failure                                                                           |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------- |
| Necessity          | Does this solve a repeated user job that native HTML or an existing composition cannot solve clearly?                     | It exists only because another catalog had it, or because a CSS class was available.      |
| Ownership          | What does the component own, and what must remain host data, policy, transport, persistence, rendering, or authorization? | The component fabricates business behavior or hides a host responsibility.                |
| Semantics          | Is the native root, name, role, relationship, and reading order correct before ARIA is added?                             | ARIA compensates for the wrong element or the public root is incidental.                  |
| State model        | Are every reachable state, transition, cancellation, failure, and recovery path explicit?                                 | Only the happy-state screenshot exists, or loading erases user context.                   |
| Interaction        | Can pointer, keyboard, touch, assistive technology, and reduced-motion users complete the same job?                       | A path depends on hover, drag, color, or precise pointing alone.                          |
| Information design | Is the primary value, next action, consequence, and secondary detail ordered correctly?                                   | Every element competes equally or the primary action is ambiguous.                        |
| Adaptation         | Does it survive 320px, 200% zoom, long Chinese and German copy, RTL, coarse pointers, and virtual keyboards?              | Content clips, controls shrink below target size, or DOM order becomes wrong.             |
| Visual system      | Does it use shared tokens, density, boundaries, focus, and semantic colors without inventing a private visual world?      | It relies on nested cards, decorative gradients, arbitrary radii, or color-only state.    |
| Engineering        | Is the contract explicit, controller idempotent and scoped, adapters thin, and source separated by concern?               | Runtime behavior is duplicated by framework adapters or one file owns unrelated concerns. |
| Evidence           | Do source, manifest, docs, examples, tests, screenshots, and accessibility output prove the same contract?                | A generated placeholder or shallow selector is treated as completion.                     |

### Adversarial questions

Before implementation, the reviewer must try to invalidate the component:

1. Remove it and use native HTML. What user capability is lost?
2. Replace it with existing components. What durable coordination or meaning is still missing?
3. Supply empty, partial, stale, denied, offline, slow, malformed, and excessively long content. Does the job remain understandable and recoverable?
4. Complete the job with keyboard only, screen-reader browse mode, touch only, reduced motion, RTL, 200% zoom, and a 320px viewport.
5. Repeat or reject the primary action. Is duplicate execution prevented, prior state restored, and focus returned predictably?
6. Mount two instances, initialize twice, unmount during work, and update controlled state externally. Does behavior remain scoped and deterministic?
7. Use the native, React, and Vue examples side by side. Do they render the same semantic root, parts, events, methods, and state?
8. Ask which visual detail communicates hierarchy or state. If the answer is decoration rather than information, remove it.

## Decision vocabulary

| Decision          | Meaning                                                                                                                                             |
| ----------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Keep**          | A durable standalone job exists. Improve the contract and experience without widening ownership.                                                    |
| **Narrow**        | The job is valid, but the current contract owns too much or overlaps a neighbor. Reduce it to one responsibility.                                   |
| **Compose**       | The job is real, but existing primitives should express it. Keep a documented and tested recipe rather than a distinct controller or styling world. |
| **Demote**        | This is a utility, part, or recipe rather than a public component. Preserve a compatibility alias until the next major release.                     |
| **Host boundary** | Keep an A3S frame and semantic integration contract while the host owns the engine, data, transport, policy, or trusted renderer.                   |

Priorities are dependency and risk priorities, not visual prominence:

- **P0** blocks coherent work elsewhere or carries high interaction, accessibility, or compatibility risk.
- **P1** is a common composite or state-rich component built after its primitives and shared kernels stabilize.
- **P2** is a low-risk presentation primitive or specialist surface that still requires complete evidence.

## Universal completion contract

Every retained component is complete only when all applicable proof exists:

1. One-sentence user job, use-when, do-not-use-when, ownership boundary, and realistic content ranges.
2. Canonical root and parts, native semantics, public states, events, methods, cancelable authorization points, and controlled updates.
3. Default, hover, focus-visible, active, disabled, loading, empty, error, success, selected, open, cancellation, and recovery states where reachable.
4. A visual specification using the shared blue-default token system, typography, 4px spacing scale, radii, elevation, icon sizes, and one-primary-action rule.
5. Keyboard map, focus entry and return, screen-reader names and relationships, 44px coarse-pointer targets, reduced motion, and WCAG AA contrast.
6. 320px and 390px phone, 768px compact, 1440px desktop, 200% zoom, long localized copy, RTL, dark mode, and no-horizontal-overflow evidence.
7. Native HTML, React, and Vue examples that perform the real job. Stateful components use the matching hook or composable against the same controller contract; generic placeholder children are forbidden.
8. Deterministic A3S Test coverage for the primary path, keyboard path, one failure/recovery path, console and page errors, and an accessibility snapshot.
9. Visual baselines for the meaningful state matrix, batched across light/dark and desktop/mobile. A screenshot of the default state alone is insufficient.
10. Updated manifest, package exports, types, bilingual docs, Playground composition when applicable, migration notes, and no hand-edited generated output.

## Shared kernels and execution order

The catalog must not be optimized as 116 unrelated mini-products. Work proceeds through shared kernels so later components inherit proven behavior.

```text
Foundations and semantic contract
  -> action, field, choice, focus, layer, and status kernels
    -> primitive controls and content surfaces
      -> navigation, overlays, collections, and application frames
        -> Harness task, conversation, execution, and tooling compositions
          -> Playground combinations and release-wide visual audit
```

### Wave 0 — Contract decisions and migration safety

- Resolve Spinner and Scroll Area as utilities or components; do not keep contradictory public claims.
- Add canonical roots or documented contract exceptions for Radio Group, Theme Switcher, Tooltip, native Select, and other incidental selectors.
- Lock the boundaries among Card, Item, Resource Card, Artifact Card; App Shell, Task Workspace, Agent Workbench; and Execution Item, Tool Call, Terminal, Log Viewer, Execution Evidence.
- Define compatibility aliases, deprecation notices, versioned docs, and removal timing before changing public selectors.

### Wave 1 — Foundations and high-leverage primitives

- Stabilize color, focus, density, typography, spacing, motion, layer, and responsive tokens.
- Build shared action, field, choice, menu, overlay, status, code-surface, and collection-state anatomy.
- Complete Button, Form, Field, Input, Textarea, native and custom selection, Tabs, core overlays, Toast, Card, Icon, Table, Tree, App Shell, Theme Switcher, and their evidence.

### Wave 2 — General composites

- Complete search, navigation, feedback, content, media, data, and application components in dependency order.
- Split controllers over 500 lines and separate positioning, selection, data projection, persistence-free state, and DOM lifecycle concerns.
- Replace all generic framework examples with runnable equivalents of the native examples.

### Wave 3 — Harness foundations

- Complete Task Workspace, Agent Composer, Agent Transcript, Approval Request, Execution Item, File Explorer, Code Editor, Terminal, and Device Simulator first.
- Build remaining Harness contracts as narrow parts or compositions on those foundations; do not create a second shell, state badge, card, or disclosure grammar.

### Wave 4 — Composition and release audit

- Rebuild the standalone Playground around real end-to-end tasks, failure/recovery, narrow layouts, dark mode, and RTL.
- Run the full documentation, framework, boundary, package, A3S Test, visual, accessibility, and detector gates.
- Promote a component only when its issue contains the full evidence bundle and an adversarial reviewer cannot invalidate its necessity or boundary.

The following decisions are implementation directives. “Compose” and “Demote” preserve current compatibility until the documented migration boundary; they do not authorize an immediate breaking removal.

## Issue template

Each component becomes one tracked issue using this fixed structure:

1. **Decision and defense** — Keep, Narrow, Compose, Demote, or Host boundary; repeated user job; native/composition alternative; non-goals.
2. **Current evidence** — source files, current screenshot, manifest row, docs, adapter output, tests, known consumers, and compatibility constraints.
3. **State and content matrix** — minimum, typical, maximum, empty, loading, partial, denied, offline, error, success, disabled, selected/open, cancellation, and recovery as applicable.
4. **Interaction contract** — semantic root and parts, keyboard map, focus entry/return, touch behavior, events, methods, controlled updates, and host authorization points.
5. **Visual specification** — hierarchy, measurements derived from tokens, responsive topology, dark/RTL/reduced-motion behavior, and component-specific do-not rules.
6. **Implementation slices** — CSS, controller, manifest, adapters, bilingual docs, Playground, migration, and tests. Each slice is independently reviewable.
7. **Adversarial evidence** — A3S Test result IDs, light/dark desktop/mobile screenshots, accessibility tree, console/page-error output, and the reviewer's failed attempts to break the contract.

## Release gates

A wave can merge only when:

- Every included component has a recorded decision and scores at least two in every critical review dimension.
- No public example contains placeholder component content, fabricated behavior, or a framework-only contract.
- No retained controller exceeds 500 lines or mixes unrelated lifecycle, positioning, data, and interaction concerns.
- A3S Test scenarios exercise the primary interaction, keyboard path, and one failure/recovery path rather than only checking presence.
- Visual evidence covers meaningful states in light/dark and desktop/mobile, plus RTL or reduced motion where direction or animation matters.
- Accessibility output proves names, relationships, focus, inertness, live-region bounds, and reading order.
- The component's source, manifest, package entry, React/Vue adapters and hooks, bilingual docs, Playground use, and tests agree.
- Compatibility aliases and deprecations have migration guidance and versioned documentation.
- The documentation build, package checks, framework checks, boundary checks, A3S Test suites, visual suite, and mechanical design detector all pass from a clean generated build.

## Progress tracking

The plan itself is the source of truth until component issues are created. Replace each row's priority with an issue link and status only after the issue contains its decision defense and current evidence. “Implemented” is not a terminal state; the only terminal state is **Verified**, backed by the complete proof bundle above.
